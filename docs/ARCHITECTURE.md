# Architecture — board-only v0.6.1

The main-process `TunnelService` owns a single explicitly opened DAQ transport, binary decoder, device clock, calibration state and recorder. The renderer owns navigation, forms and bounded display histories. It cannot access Node, files, serial writes or arbitrary IPC. The preload exposes one typed method per task, and main handlers validate sender, frame, origin and action schema. Context isolation and sandboxing remain enabled.

## Acquisition path

`SerialDaqTransport → binary byte chunks → DaqDecoder → DeviceClock → immutable sample → recorder + latest snapshot → React`

DAQ acquisition starts disconnected with empty measurements. There is no synthetic data generator, simulator action, ASCII/auto response selection, or simulated actuator/motion state. Only the verified RP2350 USB identity 2E8A:F00F can be opened by the DAQ transport. Metadata scanning does not open other ports. DAQ connection is always an explicit operator action; the separate Pitot connection homes automatically on startup.

The response format matches `LabVIEW::MeasurementWrite` in the supplied firmware's binary branch: one bank byte, N native little-endian float32 values, then a little-endian uint32 microsecond timestamp. Counts are 4/4/1/4/24 for banks 02/03/04/05/06. D0/E0/E1 text is bounded and retained. Original zeros and nonfinite values remain visible; nonfinite values serialize as null plus a raw-special tag. Timestamp deltas accumulate across wraps; a backwards clock fault halts acquisition state until reconnect.

The format has no checksum or general synchronization marker. The decoder cannot guarantee recovery after arbitrary corruption. Raw byte counters and capped 80-chunk previews remain independent of decoding. Recording keeps complete received chunks. UI refresh is decimated and is never the source of recorded samples.

## Commands and lifecycle

Connect opens the selected serial endpoint with 8N1 and no flow control, asserts DTR/RTS, attempts DAC zero, then sends an all-measure command with a big-endian microsecond period. Missing DAC acknowledgment is a fan-initialization warning, not a connection failure; acquisition continues if USB is healthy. Actual transport errors still follow the connection-loss path. ALL_MEASURE resets firmware measurement states, so a preceding STOP is unnecessary. The service spaces writes by at least 250 ms: firmware `CheckReceive` consumes all currently available bytes as one request's arguments rather than enforcing packet boundaries.

The protocol has no VFD run-state telemetry. The application does not infer it from pressure or DAC acknowledgment and has no operator-confirmation state, action, popup or readiness gate. Once connected with acknowledged DAC zero, fan percentages can be applied directly. Existing connection, DAC acknowledgment, range, pacing and Emergency Stop checks remain independent of the physical VFD Run/Stop controls.

DAQ actions are serialized. Serial operations have a three-second timeout. The DAQ write path permits exact acquisition commands 00/01 and DAC command 21 capped at 3000 mV. `fanMillivolts` validates 0–100% and maps to integer millivolts. `FanOutput` requires an exact D0 firmware acknowledgment, enforces initial zero before a nonzero output, and reports confirmed/unverified/sending/error state. A nonzero acknowledgment failure latches the stop state and attempts zero. There is no raw serial-write API or PID. DAQ validation rejects motion, simulation and response-format actions; typed Pitot actions use a separate IPC handler and transport.

Emergency Stop synchronously latches the main-process block before awaiting the action queue, then requests DAC zero. Every transmit rechecks the latch after pacing; only zero is allowed while latched. New Stop requests supersede older queued nonzero references, including an unsent reference waiting for pacing. References cannot transfer across connection versions. Reset sends no command and never restores output. Normal disconnect/shutdown requests acknowledged zero before releasing the port, including when latched. Incoming data remains available. A clock fault suppresses further measurement updates but still processes DAC acknowledgments/diagnostics. Software cannot recall bytes handed to the transport or guarantee physical stopping on USB loss or process/power failure.

The renderer's `OperatorSettings` stores requested fan percentage, local Pitot target, airspeed units and editable pressure-source mappings. Fan dragging/editing is local until Apply; Stop sends zero. The applied DAC acknowledgment is separate from the requested percentage and is not a measurement of actual motor speed/voltage. Reconnect and Emergency Stop reset the dial. Main/Pitot/Force Balance/Pressure graphs/Data Viewer/Pressure array provide the primary instrument views, with calibration, session and hardware pages retained.

`PitotService` owns a separate `SerialPitotTransport`, verifies the observed Pitot Marlin machine/UUID/emergency-parser identity, restores captured original runtime limits, checks settings/endstops, and homes only X/Y on every connection. Startup attempts this automatically after showing the window. DAQ connection remains explicit. Typed `pitotAct` IPC exposes connect/disconnect/home/move/stop only, with Z, raw G-code and targets outside X0–360/Y0–360 mm rejected. The axes map directly to the controller; the larger native Y400 limit is not used. One command can await `ok` at a time; simultaneous actions are rejected rather than queued. `planPitotMove` splits the straight target path at 5 mm end-zone crossings and uses 300 mm/min there, 4000 mm/min in the interior. Stationary axes do not trigger end-zone slowing. Each segment waits for `M400` and matching `M114`, with a deadline calculated from distance/feed plus margin. Busy messages cannot extend a deadline. Stop/USB loss/reset/timeout invalidate homing and cancel the operation generation, preventing subsequent segments/commands. `M112` bypasses normal acknowledgement waits; the global stop initiates it immediately alongside DAQ zero. There is no automatic M999/reset/resume. Snapshots are pure reads: navigation and idle time never invalidate homing. Runtime `M84 S0` disables the inactivity timeout without disabling motors. There are no routine motor-release commands, EEPROM writes or firmware uploads. See [Pitot implementation](PITOT-2026-11-19.md).

Disconnect/USB loss stops acquisition, marks retained samples stale, and finalizes recording. Reconnect resets frame counters, timestamps and measurement/display histories. A lost connection cannot silently switch to generated data. Acquisition, calibration and recording require a live connection; recording file-picker results are checked against the same connection session before file creation. Export waits for any in-progress recording close.

## Measurements and storage

Hardware calibration uses `reference = raw × scale + offset` with canonical units, versioning, least-squares fits and explicit fresh-reading tare. No archived calibration is activated automatically and no raw bridge counts are labeled Newtons without calibration. Changes apply to subsequent samples; recorded history is immutable. Only `hardware-calibrations.json` is loaded.

Derived airspeed uses canonical Pa/kPa inputs, manual room temperature and the uncorrected Bernoulli relation. A finite differential pressure in [−3, 0] Pa is clamped to zero only inside the calculation. Pressures below −3 Pa, invalid/nonfinite inputs, bad atmospheric density inputs and stale readings suppress that result. The display explains the clamp or unavailable result. Original signed pressures, graphs and recordings are untouched. Sensor calibration, channel mapping, operating limits and physical accuracy remain commissioning work.

`TunnelService` retains the latest valid positive kPa atmospheric measurement separately from the latest raw sample. Snapshots expose that measured density input for at most 2000 ms while connected. Invalid packets never overwrite it or refresh its age. Expiry, disconnect or atmospheric recalibration removes it. The atmospheric display and airspeed calculations use this bounded input with age/held labeling; original measurements and raw graphs/logs remain untouched. A two-second settling deadline suppresses only derived airspeed after acquisition starts. Snapshots publish at 100 ms. See the November 18 diagnosis for the source-driver bit-check defect.

Pitot and central-ring estimates use separate selected differential inputs (archived defaults press1 and press2) and the measured absolute pressure. Their bounded histories retain the calculated m/s value at each display update; unit changes convert for display, and mapping/session changes reset the histories. Raw graphs retain original board values, offer individual/all selection and overlay only channels sharing the same native unit. Display histories are decimated to snapshots and capped at 120 points per channel, independently of full-rate recording. Derived speeds and preview settings are not recording columns.

Recording is exclusive-create, append-only JSONL with raw RX/TX chunks, samples, metadata and diagnostic/calibration events. New session/sample records are hardware-labeled. Backpressure reports a failure instead of unbounded buffering. Abrupt power loss can still lose buffered writes; the log is not a crash-proof database.

## Verification seam

Tests inject `DaqTransport` through the service constructor and replay original November 5 capture chunks. The Electron entry exports its main-process service for desktop test injection; this export is never exposed through preload or to the renderer. Test transport implementations, fixture metadata and original captures are not shipped in `out/` or the executable package. Desktop tests exercise production IPC, decoding, recording and UI without opening a board. Pitot tests replay the November 19 identification/settings and inject motion replies. Offline desktop runs disable automatic discovery before launch with `WT_DISABLE_PITOT_DISCOVERY=1`. Production constructs `SerialDaqTransport` and `SerialPitotTransport` for their respective devices.
